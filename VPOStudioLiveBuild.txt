❯ We're building "VPO Studio", a web app that turns a topic into a              
  ready-to-publish short-video content pack. This is step 1 of 7: write the     
  project's brief and architecture. Documents only: no app code, no installs.   
  This will be a live product used by real people, so design for reliability,   
  cost control and growth from the start.                                       
                                                                                
  THE PRODUCT                                                                   
  A marketer or PM signs in and enters a topic. The app researches it, writes a 
  script, develops a creative direction into a strong prompt for an AI video    
  model, previews it as a storyboard, and packages everything for publishing.   
  People decide only where their judgement matters or money is about to be      
  spent; the app checks quality itself.                                         
                                                                                
  THE FLOW (★ = human checkpoint)                                               
  1. Brief: topic, audience, platform and aspect ratio (9:16 or 16:9), duration 
  (15–60s), target video model (default Veo 3.1), optional source links or      
  notes. Brand details come pre-filled from the user's Brand kit. OR the user   
  pastes their own script and skips to stage 3.                                 
  2. ★ Story: in one job, Gemini with Google Search grounding produces 5–8 key  
  facts, then a timestamped script built only from those facts, in beats like   
  "[0:00–0:05] VISUAL: … VO: … ON-SCREEN: …". Sources come ONLY from grounding  
  metadata, never from links the model writes. Each fact is labelled "stated"   
  or "implied" by its source. A script length check with no AI compares the     
  word count with the duration at a set speaking rate. The user reviews facts   
  and script on one screen: removing a fact rewrites the script without it; the 
  script is editable.                                                           
  3. ★ Direction: 3 short creative directions (name, hook, angle, look, mood,   
  one-line summary). The user picks one, optionally with a note. The app then   
  writes the full video prompt for that direction, scores it on 5 dimensions    
  (overall = the weakest), and improves it until it passes a set threshold, up  
  to a set number of attempts. The score is shown.                              
  4. ★ Look: after showing the estimated cost and getting confirmation, render  
  one key frame that sets the character and visual style. The user approves it, 
  asks for a change with a note, or uploads their own image instead (free).     
  5. Storyboard: the remaining frames (up to 6 in total, one per beat) are      
  rendered using the key frame as a reference. A reviewer scores each frame on  
  6 dimensions; frames below the threshold are regenerated once automatically.  
  The user can regenerate any single frame with a note.                         
  6. Pack: generated automatically and editable: the final video prompt and     
  negative prompt for the target model, title, captions for Instagram Reels,    
  YouTube Shorts and LinkedIn, hashtags, thumbnail text, posting notes.         
  7. ★ Approve: the user approves the pack, then downloads it as a zip, copies  
  parts of it, or sends it to a Telegram chat.                                  
  Brand kit: saved once per user (brand name, palette, character description,   
  tone, constraints, preferred platforms) and applied to every run.             
  Autopilot (built in step 7, designed for now): runs straight through with     
  defaults, stopping only at cost confirmations and the final approval.         
  Every run is saved with its current stage, listed on the user's History page, 
  and can be reopened.                                                          
                                                                                
  THE 7-STEP BUILD PLAN                                                         
  1 (now): AGENTS.md and architecture docs.                                     
  2: frontend with every screen on sample data, deployed to Vercel.             
  3: backend, test mode, cost tracking, and the Story stage.                    
  4: Direction, Look and Storyboard.                                            
  5: Pack and Approve, Supabase (database, storage, user accounts, Brand kit),  
  Telegram.                                                                     
  6: backend deployed to Render, whole flow live end to end.                    
  7: hardening: Autopilot, per-user daily limits, a Usage page, error tracking, 
  full error states, README.                                                    
                                                                                
  DECISIONS ALREADY MADE                                                        
  - One repository: /frontend (Next.js App Router, TypeScript, Tailwind)        
  deployed on Vercel; /backend (Node, TypeScript, Express) deployed on Render.  
  - Long jobs run on the backend; the frontend polls the run's status. Job      
  state is saved with the run, never only in memory, so a restart marks a job   
  "interrupted" and lets the user resume it. The backend holds no important     
  state in memory, so it can be restarted or run as several copies.             
  - Gemini through the official @google/genai SDK. Every model ID is an         
  environment variable, with separate settings for the main writing model, a    
  cheaper model for scoring and reviewing, and the image model. Before choosing 
  defaults, check Google's current Gemini API documentation for current model   
  IDs (some older image models are being retired) and their prices, and record  
  both, with the date, in DECISIONS.md. The health check confirms the           
  configured models exist.                                                      
  - Quality checks are automatic: scores with thresholds and a capped number of 
  retries, all set in settings. Users judge outcomes, not prompts.              
  - Cost tracking: every AI call is logged with its model, token counts or      
  image count, and estimated cost, using prices stored in settings. Each run    
  shows its running cost. Before any image generation, show the estimated cost  
  and require confirmation. Limits on frames, retries and regenerations per run 
  are settings.                                                                 
  - Rate limits: at most a set number of Gemini calls at once. On a rate-limit  
  error, wait and retry at most twice, and show the user what's happening. Any  
  other error is shown in full and never retried automatically.                 
  - Research results for the same user and topic are reused for 24 hours unless 
  the user asks for a fresh run.                                                
  - Supabase (Postgres, Storage and Auth) from step 5. Until then the backend   
  saves runs as local JSON files behind one storage module, so switching to     
  Supabase changes that module only. From step 5, every run and Brand kit       
  belongs to a user, the owner is always set on the server from the session,    
  and every query is scoped to the signed-in user.                              
  - TEST_MODE, on by default: every AI call returns realistic sample output,    
  including sample images, at zero cost. The interface shows a "TEST MODE"      
  badge whenever it's on.                                                       
  - Secrets live only in .env files, which are gitignored and server-side. The  
  Gemini key never reaches the browser and is never logged. Commit .env.example 
  files instead.                                                                
  - A frontend with no backend address set shows sample data and a "SAMPLE      
  DATA" badge.                                                                  
  - The people using this are non-technical. Never ask them to run Terminal     
  commands: run commands yourself and explain in plain English.

  3. Publishing to GitHub and deploying to Vercel (no Terminal)

  A. Push this repo to GitHub from VS Code:
  1. Open the Prompt optimizer folder in VS Code.
  2. Click the Source Control icon in the left sidebar (looks like a branching
     icon).
  3. Click Publish to GitHub (VS Code shows this automatically since the repo
     has commits but no remote yet).
  4. Choose a repository name, pick Private or Public, and confirm. VS Code will
     ask you to sign in to GitHub the first time — follow its prompts.
  5. Once done, VS Code shows a notification with a link to the new GitHub
     repository.

  B. Deploy on Vercel from the browser:
  1. Go to vercel.com and sign in (you can sign in with your GitHub account
     directly).
  2. Click Add New… → Project.
  3. Select the GitHub repository you just published.
  4. On the configuration screen, set Root Directory to frontend (important —
     the repo root has /frontend and /backend, and Vercel needs to know only
     /frontend is the Next.js app).
  5. Leave the framework preset as Next.js (Vercel detects it automatically) and
     the build command as default.
  6. You can leave Environment Variables empty for now — with no
     NEXT_PUBLIC_API_URL set, the app runs on sample data with the "SAMPLE DATA"
     badge, exactly like it does locally.
  7. Click Deploy. Vercel builds and gives you a live .vercel.app URL when done.
